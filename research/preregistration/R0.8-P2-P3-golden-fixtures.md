### R0.8-F2: golden fixtures P2/P3, entradas y salidas congelables

#### Naturaleza del artefacto

Este documento complementa `R0.8-P2-P3-contract.md` (F1) sin modificar sus
invariantes. El conjunto F2 contiene **15 variantes en las 10 familias G01-G10**,
con 12 grafos esperados, cinco diferenciales esperados y ocho variantes de
rechazo. Los casos son sintéticos y no contienen trazas confirmatorias.

Los archivos fueron escritos **antes** del proyector de producción R0.8-I.
Las expectativas se obtuvieron con un procedimiento independiente de autoría
basado en SHA-256 y serialización JSON de la biblioteca estándar, apoyado en los
schemas y el validador de trazas ya congelados en R0.7. R0.8-I no puede modificar
los resultados golden para hacer pasar sus algoritmos. F3 revisará y congelará
formalmente esta versión; hasta entonces el contrato es un candidato `v0.1`.

#### Archivos

```text
tests/fixtures/provenance/r0_8/
    inputs.json
    expected.json
    SHA256SUMS
tests/provregress/test_provenance_golden_fixtures.py
```

`inputs.json` y `expected.json` son **un único objeto JSON canónico por archivo**,
codificado en UTF-8, con claves ordenadas, separadores compactos y un salto de
línea final. `SHA256SUMS` conserva el SHA-256 de los bytes completos de cada uno.
No se usan placeholders, valores aleatorios ni timestamps generados en ejecución.

El test de F2 revisa checksums, precondiciones de R0.7, identidades de nodos,
orientación de aristas, DAG, contenido de grafos, claves de DeltaG y los
resultados esperados. Es un test de **consistencia del corpus**, no un segundo
proyector ni un test de conformidad de R0.8-I, que todavía no existe.

#### Esquema exacto de entrada

Raíz de `inputs.json`:

```json
{"schema_version":"r0.8-golden-inputs-v1","cases":[{"id":"G02","variant":"equivalent-unique-event","traces":{"baseline":[],"candidate":[]}}]}
```

El ejemplo anterior expresa únicamente el *esqueleto* del índice: los eventos
reales están completos en el archivo. Cada caso incluye:

- `id`: familia `G01` a `G10`;
- `variant`: nombre estable de la variante;
- `traces`: mapa de roles `baseline` y, cuando procede, `candidate`; cada traza
  es una lista ordenada de diccionarios `EventEnvelope` de R0.7;
- `graph_to_validate`: opcional; grafo explícitamente manipulado para el caso
  `G07/explicit-dag-cycle`. Es entrada exclusiva al validador DAG, no resultado
  del proyector sobre la traza válida suministrada.

Una traza positiva utiliza `run_id`, `event_id`, `sequence`, timestamps UTC,
`app_id`, `case_id`, `condition_id`, `repeat_index`, `component_type`,
`component_id`, `event_type`, `payload_hash`, `payload_ref`, `attributes` y
`error`, conforme a R0.7. El payload se representa por su digest declarado;
cuando se desea probar el camino sin referencia, `payload_ref=null`.

#### Esquema exacto de salida: grafo

Raíz de `expected.json`: `schema_version="r0.8-golden-expected-v1"` y `cases`.
Cada registro conserva `id` y `variant`. Para un caso válido incorpora:

- `graphs`: mapa de rol a grafo completo;
- `delta`: diferencial completo cuando existen ambas trazas, `null` si no;
- `reprojections`: número de reproyecciones idénticas exigidas al implementar
  el test de conformidad, normalmente `1`, `2` en G01.

El grafo utiliza exclusivamente estos campos de primer nivel:

```text
schema_version = provenance-graph-v1
run_id, app_id, case_id, condition_id, repeat_index, system_version_id
trace_hash = null
nodes: lista por node_id ascendente
edges: lista por edge_id ascendente
graph_hash = SHA-256 del objeto anterior sin graph_hash
```

`trace_hash=null` significa que F2 ofrece `EventEnvelope` en memoria, **no un
JSONL cerrado cuyos bytes hayan sido verificados**. No se debe reemplazar el
valor por un digest inventado. En implementaciones futuras, un JSONL real podrá
aportar ese campo conforme a otra entrada y test explícitos.

Campos por clase de nodo, además de `node_id` y `node_kind`:

| Clase | Campos obligatorios |
| --- | --- |
| `component` | `component_type`, `component_id` |
| `event` | `event_id`, `sequence`, `timestamp_utc`, `event_type`, `component_type`, `component_id`, `payload_hash`, `attributes`, `error` |
| `payload` | `payload_hash`, `payload_ref` |

Las relaciones parentales se codifican mediante aristas `observed_parent`, no
mediante un campo duplicado `parent_event_ids` en el nodo de evento. Los demás
campos observables especificados para el nodo de evento sí se preservan.

Cada arista contiene exactamente `edge_id`, `edge_kind`, `source_node_id` y
`target_node_id`. Los únicos tipos son `emits`, `observed_parent` y `produces`.

Las fórmulas de F1 se conservan literalmente. Para reproducir un identificador:

```text
H(x) = sha256(JSON_canónico_UTF8(x))
component_id = H(["r0.8.node.v1",run_id,"component",component_type,component_id])
event_id     = H(["r0.8.node.v1",run_id,"event",event_id])
payload_id   = H(["r0.8.node.v1",run_id,"payload",payload_hash.value])
edge_id      = H(["r0.8.edge.v1",edge_kind,source_node_id,target_node_id])
```

En esas expresiones, los `component_id` y `event_id` de la derecha son los
identificadores observados de R0.7; las variables de la izquierda representan
las identidades internas SHA-256 de P2. No son equivalentes.

Un mismo digest se representa por un solo nodo `payload` dentro del run.
Sus referencias deben ser compatibles; el comportamiento ante referencias
contradictorias para el mismo digest debe quedar expresamente rechazado en I2.
F2 solo contiene referencias compatibles.

#### Esquema exacto de salida: DeltaG

El diferencial posee `schema_version="provenance-delta-v1"`,
`baseline_run_id`, `candidate_run_id`, las listas siguientes y `delta_hash`:

| Campo | Forma de cada entrada |
| --- | --- |
| `node_added`, `node_removed`, `node_unchanged` | Clave semántica JSON, lista de cadenas |
| `node_changed` | Objeto `{key: [...], changed_fields: [...]}` |
| `node_ambiguous` | Objeto `{key: [...], baseline_count: N, candidate_count: N}` |
| `edge_added`, `edge_removed` | Objeto `{edge_kind: str, source_key: [...], target_key: [...]}` |
| `edge_ambiguous` | Objeto anterior más `side` (`baseline` o `candidate`) y `count` |

Las claves de componente, evento y payload mantienen las reglas de F1. Los
cambios de evento solamente comparan `payload_hash`, `attributes` y `error`.
`event_id`, `sequence`, `timestamp_utc`, `run_id` y la versión del sistema
**no son criterios de cambio observable**. Las diferencias de aristas se
calculan por claves semánticas, no por IDs internos de ejecución.

Las listas de resultados están ordenadas ascendentemente por los **bytes JSON
canónicos de cada entrada**. `delta_hash` se calcula sobre el registro completo
sin el propio campo `delta_hash`. Así se pueden comparar resultados byte a byte.

Las aristas incidentes en nodos ambiguos se registran en `edge_ambiguous` por
lado, agrupadas con su multiplicidad. Nunca se declaran añadidas ni retiradas
por un emparejamiento arbitrario. Esta convención de formato será revisada en F3.

#### Esquema exacto de salidas negativas

Un caso rechazado contiene solamente `id`, `variant` y:

```json
{"error":{"stage":"projection","code":"non_prior_parent"}}
```

Los valores cerrados del corpus son:

| Etapa | Códigos en F2 |
| --- | --- |
| `schema` | `reserved_attribute` |
| `projection` | `non_prior_parent`, `non_contiguous_sequence` |
| `graph_validation` | `cycle` |
| `comparison` | `case_mismatch`, `app_mismatch` |

El campo `code` fija la **categoría semántica** de rechazo, no el texto exacto
de una excepción ni su traceback. El error debe ocurrir en la etapa indicada.
No se acepta que un caso negativo produzca parcialmente un grafo o DeltaG.

#### Cobertura de las familias golden

| ID | Variantes | Expectativa discriminante |
| --- | --- | --- |
| G01 | `reproject-and-deduplicate` | Dos proyecciones idénticas, payload compartido |
| G02 | `equivalent-unique-event` | Sin cambios aunque varíen run, evento y reloj |
| G03 | `payload-change` | Evento cambiado, payload retirado/añadido y aristas `produces` distintas |
| G04 | `explicit-parent-added` | Solo se agrega `observed_parent` |
| G05 | `independent-reorder` | Permutación sin dependencia declarada, DeltaG vacío |
| G06 | `ambiguous-repeated-event` | Grupo ambiguo de dos invocaciones por lado; aristas ambiguas |
| G07 | `future-parent`, `sequence-gap`, `cycle-via-future-parent`, `explicit-dag-cycle` | Rechazo de traza inválida o ciclo de grafo adulterado |
| G08 | `case-mismatch`, `app-mismatch` | Rechazo de comparación incompatible |
| G09 | `reserved-attribute`, `nested-reserved-attribute` | Rechazo de filtración de etiquetas privilegiadas |
| G10 | `hash-without-artifact-ref` | Grafo permitido, sin afirmación de verificación de bytes |

Para G07, una **traza válida no puede tener un ciclo de padres**, porque R0.7
exige padres anteriores al hijo. La variante `cycle-via-future-parent` falla
antes de proyectar. `explicit-dag-cycle` aporta, por separado, un grafo con
aristas `observed_parent` en ambas direcciones, IDs correctos y hash coherente;
el validador DAG debe rechazarlo pese a su serialización válida.

#### Protocolo de aceptación F2 y siguiente paso

Desde la raíz del repositorio y con `.venv` activo:

```bash
python -m pytest -q tests/provregress/test_provenance_golden_fixtures.py
python -m pytest -q
python -m pip check
git diff --check
```

Verificar los bytes desde el directorio al que pertenecen las rutas relativas
de `SHA256SUMS`:

```bash
(cd tests/fixtures/provenance/r0_8 && sha256sum -c SHA256SUMS)
```

Una vez aprobados esos gates y la revisión F3, los ficheros golden se tratan
como oráculo inmutable para R0.8-I. Cualquier corrección posterior requiere
motivo documentado y una nueva versión explícita del corpus; no se alteran
expectativas silenciosamente para adecuarlas a una implementación.

R0.8-F2 no implementa projector, alignment ni DeltaG de producción, no ejecuta
modelos y no declara resultados empíricos de Paper 1.
