### R0.8-F3: auditoría y congelación formal P2/P3

#### Dictamen y alcance

**Dictamen: APTO PARA FREEZE V1, condicionado a los gates de integración local.**

Este documento fija el contrato técnico de referencia de R0.8, sin ejecutar
algoritmos de producción ni experimentos. La versión congelada es
`r0.8-provenance-contract-v1`, que incorpora por referencia F1 y F2 con sus
huellas exactas indicadas abajo. Los identificadores de serialización siguen
siendo `provenance-graph-v1` y `provenance-delta-v1`.

F1 denominó su diseño candidato `v0.1` y F2 denominó congelables sus fixtures.
F3 constituye la **decisión de adopción como v1** de aquellos archivos exactos;
no modifica retroactivamente su contenido o sus SHA-256. El commit final de F3
identifica el freeze en el historial Git; no se escribe un SHA de commit aún no
existente en un archivo bajo control de versiones.

R0.7 permanece congelada. El cierre aquí es **de especificación y oráculos**,
no un cierre experimental ni el preregistro estadístico del Paper 1.

#### Resoluciones normativas para R0.8-I

Estas precisiones explicitan decisiones compatibles con F1/F2. No autorizan
modificar los objetos golden existentes.

1. **Dos identidades distintas.** `node_id` y `edge_id` identifican objetos
   dentro de un run e incluyen `run_id` cuando corresponde. Las claves
   semánticas de P3 excluyen run, condición, versión de sistema, reloj e índice
   de secuencia. Un `graph_hash` diferente entre runs no implica una regresión.
2. **Topología observada.** Solo `parent_event_ids` crea
   `observed_parent`. No se infieren consumos, dependencia temporal, enlaces
   causales ni correspondencias por semejanza de payloads.
3. **Datos de nodo.** El nodo evento conserva los nueve campos definidos en F2.
   La relación con los padres solo existe como arista. El nodo payload es
   compartido por eventos del mismo run con el mismo digest.
4. **Referencias del mismo payload.** Para un digest compartido, las
   referencias deben coincidir estructuralmente. Una mezcla de referencias
   incompatibles se rechaza en P2, sin elegir una arbitrariamente. El caso
   negativo adicional se implementará en R0.8-I2 sin alterar G01-G10.
5. **Comparabilidad.** Para P3 deben coincidir `app_id`, `case_id` y
   `repeat_index`. Diferencias de `system_version_id`, condición o run no son
   por sí mismas `node_changed`.
6. **Eventos repetidos.** Si la clave semántica de un evento se repite en
   cualquiera de los runs, todo el grupo pasa a `node_ambiguous`. Se informan
   conteos por lado. Queda prohibido emparejar por timestamp, posición ordinal,
   ID local o similitud de output.
7. **Aristas ambiguas.** Si cualquiera de sus endpoints es un evento
   ambiguo, la arista se registra como `edge_ambiguous` con lado y
   multiplicidad; no se declara `edge_added` o `edge_removed` para esos casos.
8. **Equivalencia observable.** Un evento alineado cambia exclusivamente si
   difieren `payload_hash`, `attributes` o `error`. La topología se informa en
   las listas de aristas; los payloads se alinean por digest y no se atribuyen
   cambios de contenido a un mismo nodo de payload.
9. **Bytes frente a declaraciones.** `trace_hash=null` en todos los golden de
   eventos en memoria. Un `payload_hash` declarado sin `payload_ref` no acredita
   bytes de payload. La comprobación de bytes requiere `ArtifactStore`.
10. **Errores fail-closed.** Un input inválido se rechaza en la etapa indicada
    y no deja un grafo o delta parcial. El código/categoría del error debe ser
    semánticamente equivalente al corpus; el texto exacto de excepción no es
    objeto de comparación.
11. **Orden y formato.** Nodos/aristas por ID ASCII ascendente, entradas de
    `DeltaG` por bytes JSON canónicos, hashes del registro completo sin su
    propio campo digest. No se incluyen campos generados al vuelo.
12. **Inmutabilidad del oráculo.** Un bug del futuro código Python o Rust se
    corrige en la implementación, no alterando los resultados golden. Solo un
    defecto documentado del contrato permite crear una nueva versión de
    especificación y fixtures con autorización explícita.

#### Limitaciones y riesgos residuales

- El corpus de 15 variantes discrimina comportamientos centrales, pero no
  constituye cobertura exhaustiva de grafos, eventos ni combinaciones A1/A2/A3.
- El schema R0.7 carece de identidad universal de invocación; la ambigüedad de
  llamadas repetidas es un límite científico explícito.
- El modelo P2 es estructural: la precedencia declarada no demuestra
  causalidad, propagación de error ni superioridad sobre una traza secuencial.
- No se verifican bytes reales de artefactos en estas fixtures; ello exige
  pruebas de integración separadas con `ArtifactStore`.
- El contrato no mide mejora de localización, F1, recall, capacidad OOD ni
  significancia estadística. Esos resultados pertenecen a fases posteriores.
- Los tests del freeze no sustituyen revisión independiente, fuzzing,
  property-based testing ni controles de seguridad del runtime.

#### Puertas para declarar F3 cerrado

Desde la raíz del repositorio y con el entorno `.venv` activo:

```bash
python -m pytest -q tests/provregress/test_provenance_golden_fixtures.py
python -m pytest -q tests/provregress/test_provenance_contract_freeze.py
(cd tests/fixtures/provenance/r0_8 && sha256sum -c SHA256SUMS)
python -m pytest -q
python -m pip check
git diff --check
git status --short
```

El freeze entra en vigor **únicamente después** de que todos los gates aprueben,
se haga commit y se publique la rama. La auditoría posterior comprueba que F3
no cambió los archivos normativos de F1/F2 ni `llmtestlab` o el código R0.7.

#### Handoff a R0.8-I y control de cambios

- **I1:** Pydantic estricto de `GraphNode`, `GraphEdge`, `ProvenanceGraph` y
  `DeltaG`, conforme al formato y campos de F2, sin generar grafos.
- **I2:** projector puro, verificador DAG y pruebas de integridad de payload,
  incluida contradicción de referencias para un mismo digest.
- **I3:** alineamiento baseline/candidate conservador, explícito ante casos
  ambiguos y con comparabilidad P3.
- **I4:** differential tipado y hashes deterministas sin cambiar el corpus.
- **I5:** suite de conformidad golden completa, reproducibilidad y aislamiento
  legacy; revisiones independientes antes de proponer Rust en R0.9.

Cualquier evolución de schema, identidad, criterio de alineamiento o formato
requiere una nueva versión, pruebas de compatibilidad y un registro del cambio.
No se ejecutan investigaciones confirmatorias al cerrar R0.8-F3.
