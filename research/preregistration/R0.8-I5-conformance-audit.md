### R0.8-I5: auditoría integral de conformidad de la referencia Python

#### Objetivo y dictamen

**Dictamen técnico provisional: CONFORME EN EL NÚCLEO AISLADO.**

R0.8-I5 cierra la cadena ejecutable de referencia Python sin ampliar el schema
ni alterar los oráculos adoptados en F3. Esta auditoría no constituye un
experimento científico, ni valida superioridad de grafos, detección de
regresiones o atribución causal. El dictamen definitivo de integración depende
de ejecutar el gate completo en el repositorio del usuario, con la capa legacy
instalada, un árbol de trabajo limpio y el commit correspondiente publicado.

La cadena evaluada es:

```text
PilotFirewall -> RunContext -> RunManifest -> JsonlEventSink
    -> ArtifactStore + JSONL -> EventEnvelope -> project_trace
    -> validate_graph -> align_graphs -> diff_graphs -> DeltaG
```

Las capas ejecutables se mantienen separadas:

- **R0.7:** autorización del caso, manifests, eventos, almacén de artefactos y
  registro append-only, sin modificar la implementación congelada.
- **R0.8-I1:** schemas estrictos `ProvenanceGraph` y `DeltaG`.
- **R0.8-I2:** proyección determinista y verificación topológica del DAG.
- **R0.8-I3:** alineamiento conservador, sin correspondencias inventadas.
- **R0.8-I4:** diferencias tipadas con identidad y hashing canónicos.
- **R0.8-I5:** tests integrales y esta evidencia documental, sin alterar esos
  algoritmos.

#### Identidad de las entradas normativas

El freeze formal corresponde a `research/preregistration/R0.8-P2-P3-freeze.md`,
publicado antes de I1. Ese documento inmoviliza F1/F2 y sus SHA-256. El gate
`test_provenance_contract_freeze.py` mantiene la responsabilidad de comprobar
todos los archivos normativos. La prueba I5 añade la comprobación directa de:

| Archivo | SHA-256 de los bytes completos |
| --- | --- |
| `tests/fixtures/provenance/r0_8/inputs.json` | `9d2be2dd2d894e7c4c7508cad0bb6160147dc01d82e3d1090e7903a69d9eb242` |
| `tests/fixtures/provenance/r0_8/expected.json` | `47fd5e198f25704ee0fbc6363ea3621754397aad9ca72507be4a68752fa4be50` |

Los hashes y expectativas **no se regeneran** para adecuarlos al código de
producción. La identidad del commit final I5 se registrará en Git después de
su publicación; no se inventa un SHA futuro en esta especificación.

entorno de pruebas global no debe atribuirse sin evidencia a ProvRegress; la
verificación definitiva utiliza exclusivamente el entorno virtual del proyecto.

#### Matices de integridad y límites de la evidencia

1. **`trace_hash` no se inventa.** El SHA-256 de los bytes JSONL cerrados se
   almacena en `RunManifest`; `project_trace(events)` recibe eventos en memoria
   y deja `ProvenanceGraph.trace_hash=None`. No se declara en el grafo una
   evidencia de bytes que la interfaz actual no puede transmitir.
2. **Un digest declarado no verifica bytes.** Solo `ArtifactStore.get_bytes()`
   acredita contenido almacenado. Sin almacén, P2 verifica la identidad formal
   y los metadatos, pero no la disponibilidad o integridad física del payload.
3. **Topología observada no significa causalidad.** `observed_parent` procede
   exclusivamente de padres declarados. Ninguna prueba identifica causas raíz
   ni afirma dependencia semántica por coincidencia temporal.
4. **Eventos repetidos.** El grupo G06 conserva ambigüedad por lado. Sin una
   identidad de invocación estable, las correspondencias no se deducen por
   posición, reloj o digest del output.
5. **Errores fail-closed.** El lector JSONL expone `EventLogError` y el proyector
   encapsula fallos de traza en `ProjectionError`. Se comprueba la interrupción
   efectiva sin imponer que capas distintas compartan clase de excepción.
6. **Inmutabilidad del oráculo.** Cambios futuros del contrato requieren
   versión nueva y revisión explícita. I5 no modifica F1, F2, F3 ni sus
   fixtures; no se admiten actualizaciones automáticas de hashes esperados.
7. **Tests y límites científicos.** La conformidad con 15 fixtures sintéticos
   no aporta benchmarks de latencia, memoria, generalización, precisión de
   localización, cobertura exhaustiva ni significancia estadística.

Rechazar el gate si hay tests fallidos, errores de importación, checksums
alterados, dependencias rotas o cambios inesperados en código legacy.

#### Criterio de cierre y transición

El cierre de R0.8-I queda condicionado a:

- Gates locales aprobados con la suite completa en Python 3.11.15.
- Sin modificación retroactiva de oráculos ni archivos R0.7.
- Un único commit I5, acotado a test de conformidad y este dictamen.
- Push de la rama `r0.8-p2-p3-provenance` y revisión antes del PR hacia `main`.
- Evidencia local conservada: salida de pytest, estado Git y SHA del commit.

Después de cumplir estos puntos, R0.8 puede integrarse en `main` mediante PR.
R0.9 Rust deberá ser conforme con **los mismos bytes y hashes** de la
referencia Python. No se recomienda iniciar Rust ni una campaña experimental
antes de cerrar y revisar la integración de R0.8.
