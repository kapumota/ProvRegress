### R0.7 P0/P1: especificación técnica congelada

#### Naturaleza y límites del documento

Este documento congela el contrato **de implementación** de ProvRegress R0.7, capas P0 y P1.
No es el preregistro estadístico de Paper 1 ni habilita experimentos confirmatorios.
El preregistro experimental se definirá después del piloto, en R1.5.

La línea base de implementación es la rama `r0.7-p0-p1-foundation`, después de los
commits R0.7-C1 a R0.7-C12. La identidad definitiva del snapshot es el commit de C12,
que debe registrarse con `git rev-parse HEAD` tras su publicación. El punto verificado
previo al cierre C11/C12 es C10, `d852c403e653c8be781c6794369ddaea38ef8a7b`.

El repositorio contiene dos paquetes independientes:

- `provregress/`: núcleo de investigación y contratos R0.7.
- `llmtestlab/`: implementación heredada, mantenida como compatibilidad.

Las rutas del plan inicial `llmtestlab/experimental/` se materializaron en el
namespace independiente `provregress/`. Esta es la estructura vigente y verificable.

#### Objetivo técnico

Construir una infraestructura mínima y auditable para registrar ejecuciones
**piloto** con identidad reproducible, separación de casos, contenido direccionado
por SHA-256, eventos observables y cierre verificable de trazas.

R0.7 no genera, compara ni analiza grafos de procedencia. Tampoco ejecuta
experimentos científicos de Paper 1.

#### Contratos P0: identidad, hashing y particiones

- Todos los nuevos modelos Pydantic tienen `extra="forbid"` y validación estricta.
- `AppId`: `a1_extraction`, `a2_rag`, `a3_tools`. No equivale a `AppType` legacy.
- `ComponentType`: vocabulario cerrado de 21 tipos definido en `schema/common.py`.
- `HashRef`: `sha256`, valor hexadecimal minúsculo de 64 caracteres.
- `ArtifactRef`: digest, ruta POSIX relativa canónica, MIME opcional, tamaño no negativo.
- Serialización: UTF-8, claves JSON ordenadas, separadores compactos, sin NaN ni infinitos.
- `hash_model`: SHA-256 del `model_dump(mode="json")` canónico.
- `hash_case_ids`: rechaza blancos y duplicados, ordena IDs, calcula SHA-256.
- `DatasetManifest`: IDs únicos y ordenados, split `pilot` o `confirmatory`, hash correcto.
- `PilotStudyManifest`: conjuntos piloto y confirmatorio disjuntos, hashes correctos.

`PilotFirewall.assert_pilot_case(case_id)` acepta únicamente IDs piloto exactos.
Un ID confirmatorio o desconocido se rechaza antes de crear el contexto y antes
de invocar cualquier proveedor o callback. `filter_pilot_cases()` nunca descarta
silenciosamente casos prohibidos.

`build_run_context()` requiere un dataset con `split="pilot"`, pertenencia del
caso al dataset, consistencia de `app_id` entre dataset y sistema, y manifests
válidos. `RunContext` es inmutable y registra `run_id`, `study_id`, `app_id`,
`case_id`, `condition_id`, `repeat_index`, `system_version_id` y los hashes de
los manifests de estudio, dataset, sistema y entorno. No contiene resultados,
objetivos de mutación ni veredictos del evaluador.

#### Contratos P1: eventos, artefactos y registro

`EventEnvelope` utiliza `schema_version="pilot-event-v1"`. Los tipos válidos son:

```text
run.started        run.finished
prompt.issued      model.invoked      model.returned
retrieval.started  retrieval.returned
tool.called        tool.returned
evaluator.invoked  evaluator.scored
outcome.recorded   error.observed
```

Cada evento contiene identidad de ejecución, tipo y componente, secuencia,
instante UTC, padres, `payload_hash`, referencia opcional al artefacto, atributos
y error estructurado opcional. Los atributos observables no admiten las claves
`mutation_id`, `operator_id`, `target_component_id` ni `severity`, tampoco anidadas.
El sumidero piloto aplica también este control a payloads JSON.

`ArtifactStore` utiliza la ruta `sha256/<dos primeros hex>/<digest completo>`.
`put_bytes()` es idempotente, publica sin sobrescribir, y no sustituye archivos
corruptos. `get_bytes()` verifica tamaño y SHA-256. `exists()` no debe tratar
silenciosamente la corrupción como ausencia. No existe API de overwrite/delete.

El registro JSONL contiene exclusivamente objetos JSON canónicos en UTF-8,
una línea por evento terminada en `\n`. El append verifica el historial previo;
la secuencia comienza en 0 y es contigua, los IDs son únicos y cada padre debe
aparecer antes que su hijo. El registro corresponde a una única identidad de
ejecución y los errores de formato incluyen el número de línea.

`JsonlEventSink` recibe un `RunContext` autorizado, un `ArtifactStore` y un
archivo nuevo o vacío. `emit()` valida y almacena el payload, asigna ID,
secuencia y timestamp UTC, y añade el evento al JSONL. `close()` comprueba la
traza, impide nuevas emisiones y devuelve el SHA-256 de sus bytes exactos.

#### Manifests y ciclo de cierre

Los schemas de manifests tienen versionado explícito `pilot-*-v1`.
`MutationManifest` existe únicamente como contrato declarativo, no como motor
de inyección de fallos. Sus detalles de tratamiento constituyen información
privilegiada y no se incorporan a los eventos observables.

`RunManifest` (`pilot-run-v1`) conserva identidad de estudio, ejecución,
condición, aplicación, caso y repetición, hashes de sistema y dataset,
`mutation_manifest_hash` opcional, lista de hashes de evaluadores, hash de
entorno, estado, instante de inicio, instante final y `trace_hash` opcional.

El ciclo de cierre exige:

1. Construir `RunContext` solamente después de pasar el firewall.
2. Construir `RunManifest` inicial con estado `running`, sin `trace_hash`.
3. Emitir eventos mediante `JsonlEventSink`, almacenando payloads por contenido.
4. Finalizar con estado terminal, comprobar identidad del sumidero y fechas UTC.
5. Ejecutar `close()`, verificar el JSONL y asociar el digest exacto de la traza.

Una ejecución con estado `succeeded` necesita `trace_hash`. Una ejecución activa
no puede contener fecha final ni hash de traza. La fecha de cierre no precede a
la de inicio.

#### Seguridad metodológica y fronteras de información

- El tratamiento experimental, sus objetivos y severidad no son features visibles.
- El firewall no importa modelos, proveedores ni código de ejecución.
- Un error de validación debe detener la operación, nunca habilitar confirmatorios.
- Los manifests y traces pueden contener información sensible; no publicarlos
  automáticamente sin revisión de confidencialidad y autorización.
- Un hash de contenido prueba identidad de bytes, no autenticidad del origen.
- Los mecanismos de archivos y `flock` validados localmente no constituyen una
  garantía formal contra todos los fallos de disco, ataques concurrentes o caídas.
- Un resultado positivo de tests no equivale a validación experimental ni causal.

#### Puertas de aceptación para cerrar R0.7

Ejecutar en el entorno del proyecto, con el árbol limpio antes de incorporar C12:

```bash
source .venv/bin/activate
python -m pytest -q tests/provregress/test_legacy_compat.py
python -m pytest -q
python -m pip check
git diff --check
git status --short
git diff --stat
```

Además, verificar:

- Las pruebas históricas y nuevas aprueban sin `xfail` ni `skip` centrales.
- Los commits C1-C10 no se modificaron para introducir los gates C11/C12.
- C11 solo añadió la prueba explícita de compatibilidad.
- C12 solo añadió este snapshot y no alteró código ejecutable.
- Los commits publicados son verificables desde otra copia del repositorio.
- `main` permanece separada de la rama de trabajo hasta revisión y decisión de merge.

La evidencia de ejecución local y el SHA del commit final deben conservarse
junto con el reporte de cierre. No se inventan recuentos de tests ni hashes de
artefactos que no se hayan medido en el entorno que realiza la liberación.

#### Fuera del alcance de R0.7

- Proyección `tau(e) -> G(e)`, alineamiento y comparación de grafos.
- Operadores de mutación, campañas de fallos y benchmark experimental.
- Ejecuciones confirmatorias, estimaciones de efecto y análisis de potencia.
- GNN, causalidad confirmatoria, Rust y sistemas distribuidos de ejecución.
- Afirmaciones científicas de mejora de detección, localización o atribución.

Estas líneas pertenecen a fases posteriores y requieren contratos y evidencia
independientes. R0.8 abordará primero la especificación de procedencia,
proyección y comparación diferencial de grafos.

#### Política de cambios posteriores

El snapshot queda identificado por el commit C12 una vez que sus gates aprueben.
Cualquier modificación posterior de schemas, semántica de hashing, vocabulario
de eventos, reglas de firewall o formato persistido exige versión explícita,
pruebas de compatibilidad y justificación documentada. No editar retroactivamente
este documento para simular que la especificación previa era otra.
